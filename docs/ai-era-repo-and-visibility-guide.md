# AI 시대의 레포 구조와 작업 가시성 가이드

> 작성: 2026-11-20 / 질문: "AI로 여러 프로젝트를 동시에 개발할 때, 레포는 모노레포 vs 조직 분리? 세션·진행 상황 가시성은 어떻게 확보?"
> 적용 결과(실제 구성)는 맨 아래 [적용 결과](#적용-결과) 참고.

## 결론

**1프로젝트 = 1레포(모노레포: `frontend/`, `backend/`, `docs/`)를 권장한다. 조직·레포 분리는 협업이 실제로 생길 때 한다.**
AI가 쓰는 컨텍스트가 레포 단위로 묶이기 때문에, AI 시대에는 이 선택이 더 유리하다.

---

## 1. 모노레포 vs 레포 분리

### 지금 상황 (혼자, 다수 프로젝트, AI 자동 커밋)

| 항목 | 모노레포 (프론트+백 한 레포) | 레포 분리 (조직) |
|---|---|---|
| AI 컨텍스트 | API 스펙, DTO, 프론트 호출부를 한 세션에서 함께 본다 | 세션이 둘로 나뉘고 API 변경을 사람이 전달해야 한다 |
| 원자적 변경 | "API 필드 추가 + 화면 반영"이 한 커밋, 한 이력 | 커밋이 2개로 쪼개지고 배포 순서 문제가 생긴다 |
| 문서·기획서 | `docs/`가 한 곳, `CLAUDE.md`도 하나 | 문서를 어느 레포에 둘지 애매하다 |
| 관리 부담 | 프로젝트 N개면 레포 N개 | 프로젝트 N개면 레포 2N개 + 조직 설정 |
| CI/CD | `paths:` 필터로 변경된 쪽만 빌드 | 자연스럽게 독립 |
| 권한 분리 | 어렵다 (레포 단위 권한) | 쉽다 |

혼자 개발하고 AI가 양쪽을 다 수정하는 환경에서는 레포를 쪼갤 이유가 거의 없다.
분리의 장점(권한, 독립 배포, 팀 분업)은 지금 필요하지 않고, 단점(컨텍스트 분절, 동기화 비용)만 남는다.

### 권장 구조
```
myproject/
├─ CLAUDE.md              # AI 작업 규칙 (git 규칙, 로컬 실행법, 문서 갱신 규칙)
├─ frontend/
├─ backend/
├─ docs/
│   ├─ README.md          # 프로젝트 개요, 현재 상태 요약
│   ├─ STATUS.md          # 진행 상태 (AI가 작업 종료마다 갱신)
│   ├─ worklog.md         # 작업 이력 (날짜, 무엇을, 왜)
│   ├─ decisions/         # ADR: 주요 결정 기록
│   ├─ plans/             # 여러 세션에 걸친 작업 계획 체크리스트
│   └─ spec/              # 기획서, API 명세
├─ .github/workflows/     # paths 필터로 front/back 개별 CI
└─ .env.example
```

### 쪼개야 하는 신호 (하나라도 생기면 재검토)
- 프론트·백엔드를 **서로 다른 사람**이 맡고 권한을 분리해야 할 때
- 배포 주기와 소유 팀이 완전히 다를 때
- 백엔드 API를 **여러 클라이언트**(웹, 앱, 외부 파트너)가 공유할 때
- 레포가 너무 커져서 CI가 느려질 때

개인 계정 vs 조직(Organization)은 별개 문제다. 협업자가 1~2명이면 개인 레포에 collaborator로 초대하면 충분하다.
조직은 팀 단위 권한, 소유권 이전, 감사 로그가 필요할 때 만든다. 레포를 조직으로 transfer하는 것도 가능하므로 미리 만들 필요가 없다.

## 2. 협업이 생겼을 때의 AI 운영

혼자일 때의 "main 직접 커밋, 자동 커밋"은 협업에서는 위험하다. 최소한 다음을 바꾼다.

| 항목 | 혼자 | 협업 |
|---|---|---|
| 브랜치 | main 직접 | `feature/*` 브랜치 + **PR** |
| 병합 | 없음 | main 보호(branch protection), 리뷰 1명 이상, CI 통과 필수 |
| AI 커밋 | 자동 | AI는 브랜치에 커밋하고 **PR까지만** 만들고, 병합은 사람이 한다 |
| 작업 충돌 | 없음 | AI 세션마다 **`git worktree`**로 작업 디렉터리 분리, 이슈 단위로 분담 |
| 규칙 공유 | 개인 메모리 | **`CLAUDE.md`를 레포에 커밋**해서 팀원의 AI도 같은 규칙을 따르게 한다 |

"누가 어느 세션에서 뭘 하고 있나"는 **이슈 + 브랜치 + PR** 구조로 풀면 별도 도구 없이도 대부분 추적된다.

## 3. 병목의 본질: AI 생산 속도와 사람 검토 속도의 격차

문제는 코드량이 아니라 **사람의 인지 부하**다. 프로젝트 5개에서 AI가 동시에 일하면, 사람은 다음 세 질문에 즉답하지 못해 막힌다.

1. 지금 **무엇이 진행 중**이고, 무엇이 끝났나?
2. 어디서 **내 판단이 필요**한가? (블로킹)
3. 끝난 것 중 **무엇을 검토해야** 하고, 무엇은 믿고 넘어가도 되나?

해법은 이 세 질문에 **한 화면에서 답이 나오는 구조**를 만드는 것이다.

## 4. 가시성 확보 방안

### ① 레포 안의 문서 규약 (비용 0, 가장 먼저)
모든 프로젝트의 `docs/STATUS.md`를 같은 포맷으로 통일한다.

```markdown
# STATUS (AI가 작업 종료 시 갱신)
최종 갱신: 2026-11-20 14:30

## 🔴 사람 판단 필요 (Blocked)
- [ ] 결제 연동 방식 A/B 중 선택 필요 (decisions/0007)

## 🟡 진행 중
- 알림 기능: 백엔드 API 완료, 프론트 연동 중 (브랜치 feat/notify)

## 🟢 최근 완료 (검토 대기)
- 로그인 버그 수정 — 커밋 a1b2c3, 테스트 통과, 검토 필요도: 낮음

## ⚪ 다음 예정
- 관리자 페이지
```

핵심 규칙은 "AI가 작업을 끝낼 때마다 STATUS.md를 갱신한다"를 `CLAUDE.md`에 명시하는 것이다.
**검토 필요도(낮음/중간/높음)**를 AI가 스스로 표시하게 하면 사람이 검토 우선순위를 바로 정할 수 있다.

### ② GitHub Projects (칸반): 여러 레포를 한 보드로
- 프로젝트 N개를 **하나의 GitHub Projects 보드**에 모은다. 보드는 레포를 가로질러 쓸 수 있다.
- 컬럼은 `Backlog → AI 작업중 → 검토 대기 → 완료` 정도로 단순하게.
- AI가 작업 시작 시 이슈를 만들거나 가져오고, 끝나면 PR/커밋을 연결한다 (`gh` CLI로 자동화 가능).
- 모바일 앱으로도 볼 수 있어 이동 중 상태 확인이 된다.

### ③ 검토 부담을 줄이는 설계 (가장 효과가 큼)
가시성만으로는 부족하고, **검토할 양 자체를 줄여야** 한다.

- **자동 검증 게이트**: 테스트, 린트, 타입체크가 통과해야만 "검토 대기"로 올린다. 사람은 통과한 것만 본다.
- **위험도 기반 검토**: 문구·스타일 수정은 믿고 넘어가고, **DB 스키마, 인증, 결제, 배포 설정**처럼 되돌리기 어려운 변경만 반드시 본다. 분류 기준을 `CLAUDE.md`에 적는다.
- **PR/커밋 요약 표준화**: "무엇을, 왜, 영향 범위, 테스트 결과, 되돌리는 법"을 항상 같은 형식으로.
- **ADR(결정 기록)**: AI가 설계 선택을 했다면 `decisions/`에 "왜 이렇게 했는지"를 남긴다. 나중에 맥락 복원 비용이 크게 줄어든다.
- **작은 단위 커밋/PR**: 한 번에 큰 변경은 검토가 불가능하다. "한 PR = 한 목적".

### ④ 세션 연속성 문제 해결
AI 세션은 휘발되므로 **세션이 아니라 파일이 기억**해야 한다.

- 세션 시작 시 AI가 `CLAUDE.md` → `STATUS.md` → 최근 `worklog.md`를 읽게 한다.
- 세션 종료 시 "다음 세션이 이어받을 정보"(진행 상태, 막힌 점, 다음 할 일)를 `STATUS.md`에 기록하게 한다.
- 장기 작업은 `docs/plans/기능명.md`로 **체크리스트 계획서**를 만들고, 항목별로 체크하게 한다. 세션이 끊겨도 이어받을 수 있다.

### ⑤ 프로젝트 전체를 한눈에: 대시보드

| 방법 | 설명 | 추천도 |
|---|---|---|
| GitHub Projects 단일 보드 | 별도 구축 불필요 | ★★★ 먼저 시도 |
| 중앙 `dashboard` 레포 | 각 레포의 STATUS.md를 Actions/스크립트로 모아 README 하나로 요약 | ★★☆ |
| Notion/Linear | 외부 도구에 이슈 연동. 기능은 풍부하지만 동기화 비용 | ★★☆ 협업 시 |
| 터미널 요약 스크립트 | 여러 프로젝트의 STATUS.md를 모아 🔴 항목만 출력 | ★★★ 혼자일 때 가볍고 빠름 |
| 직접 만드는 웹 대시보드 | 레포의 STATUS를 읽어 보여주는 페이지 | ★☆☆ 오버엔지니어링 주의 |

### ⑥ 알림: 사람이 폴링하지 않게
- AI가 **🔴 판단 필요 상태**가 되면 알림(Slack, 이메일, 푸시)을 보내게 한다.
- 정상 완료는 알림 대신 **하루 한 번 요약**으로 묶는다.
- 사람이 확인하러 가는 구조가 아니라 **확인이 필요할 때만 호출되는 구조**가 병목을 없앤다.

## 5. 단계별 도입 로드맵

**1단계: 오늘 (30분)**
- 모든 프로젝트를 `frontend/ backend/ docs/` 모노레포로 정리
- `docs/STATUS.md` 포맷 통일, `CLAUDE.md`에 "작업 종료 시 STATUS 갱신 + 검토 필요도 표기" 추가

**2단계: 이번 주**
- 위험도 기준(반드시 검토할 변경 유형)을 `CLAUDE.md`에 명문화
- 테스트·린트 통과를 "완료" 조건으로 정함
- 전체 프로젝트의 STATUS를 모아 보여주는 간단한 스크립트

**3단계: 프로젝트가 늘거나 협업이 생길 때**
- GitHub Projects 단일 보드 도입
- PR 기반 흐름 + main 보호 + worktree 병렬 작업으로 전환
- 알림 자동화

**4단계: 팀 규모가 커질 때만**
- 조직 생성, 레포 분리, 권한 체계 도입

## 요약

| 질문 | 답 |
|---|---|
| 레포 구조 | 프로젝트당 1레포 모노레포. 지금도, 소규모 협업에서도 유리 |
| 조직 생성 | 권한 분리나 팀 단위 운영이 필요해질 때까지 미룬다 |
| 협업 시 변경점 | main 직접 커밋을 버리고 브랜치 + PR + 사람 병합 |
| 병목 해소의 핵심 | 가시성 도구보다 상태 표준화(STATUS.md), 위험도별 검토, 자동 검증 게이트로 사람이 볼 양을 줄이는 것 |
| 세션 문제 | 세션이 아닌 파일(STATUS, worklog, plans, ADR)이 기억하게 한다 |
