# work 모드: 회사 작업, 협업 가능성이 있는 프로젝트

> 요약: main 직접 커밋 금지, 브랜치 + PR 까지만(병합은 사람), 회사 정보 외부 전송 금지, 위험도 높음은 실행 전 확인.

**이 모드가 개인 프로젝트용 규칙(personal.md, 개인 메모리의 "main 직접 커밋, 브랜치 금지, `feat:` 커밋" 등)과 충돌하면 이 모드가 우선한다.**
개인 프로젝트의 git·실행·문서 규칙은 회사 작업에 적용하지 않는다.

## git
- main(또는 develop 등 보호 브랜치)에 직접 커밋·push하지 않는다.
- 작업마다 `feat/…`, `fix/…`, `chore/…` 브랜치를 만들어 거기에만 커밋한다.
- 브랜치를 push하고 **PR까지만** 만든다. 병합(merge)은 사람이 한다.
- PR 본문은 `review-gate.md`의 요약 표준 형식(무엇을, 왜, 영향 범위, 테스트, 되돌리는 법, 검토 필요도)으로 쓴다. 작업 레포에 원래 있던 이슈면 `Closes #번호` 로 연결한다.
- 추적 보드 카드에는 `ai-board log <번호> "PR: <URL>"` 로 PR 주소를 남긴다. 회사 레포의 PR 본문에는 개인 추적 레포 링크를 적지 않는다.
- force push, 히스토리 재작성, 남의 브랜치 수정은 명시적 요청 없이 하지 않는다.
- 커밋 메시지 형식은 해당 레포의 CLAUDE.md/CONTRIBUTING을 따른다. 정해진 게 없으면 `feat: 내용` 형식을 쓴다.
- 커밋 전에 사용자에게 묻는 절차는 두지 않는다. 단, 위험도 **높음** 변경은 실행 전에 사용자에게 확인한다.

## 병렬 작업
- 같은 레포에서 여러 AI 세션이 동시에 일하면 서로의 작업 디렉터리가 섞이지 않도록 `git worktree`로 분리한다.
- 같은 파일을 여러 세션이 동시에 수정하지 않도록, 작업은 이슈 단위로 나눈다.

## 회사 정보 보호
- 회사 코드, 데이터, 내부 URL, 시크릿을 외부 서비스(개인 GitHub 레포, 외부 AI/웹 서비스, 공개 페이지)로 보내지 않는다.
- 외부로 나가는 작업(push, 공개 게시, 외부 API 호출)이 회사 정책에 맞는지 불확실하면 먼저 묻는다.

## 문서·상태
- `core.md` 의 STATUS/worklog/ADR/plans 규칙을 그대로 적용한다.
- 팀원이 볼 수 있으므로 STATUS.md와 PR 본문은 맥락 없는 사람도 이해할 수 있게 쓴다.
