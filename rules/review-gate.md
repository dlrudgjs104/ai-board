# review-gate: 검토 부담을 줄이는 위험도 기준

사람이 모든 변경을 볼 수는 없다. 변경마다 위험도를 판정해서 STATUS.md/PR에 표기하고, 사람은 높음부터 본다.

## 위험도 분류

| 등급 | 해당하는 변경 | 사람 검토 |
|---|---|---|
| **높음** | DB 스키마·마이그레이션, 인증·권한, 결제, 배포·인프라·CI 설정, 환경변수·시크릿, 데이터 삭제·이관, 의존성 메이저 업그레이드, 공개 API 계약 변경 | 반드시. 실행 **전에** 사용자에게 확인한다 |
| **중간** | 비즈니스 로직 변경, 신규 기능, 동작이 바뀌는 버그 수정 | 훑어보기. 테스트 결과를 같이 제시한다 |
| **낮음** | 문구·스타일, 문서, 테스트 추가, 동작 불변 리팩터링(테스트 통과) | 요약만 확인, 필요 시 생략 |

판정이 애매하면 한 단계 높게 잡는다.

## 완료로 올리는 조건 (자동 검증 게이트)
- 테스트·린트·타입체크·빌드가 있으면 모두 통과한 뒤에만 🟢(검토 대기)로 올린다.
- 돌릴 수 없는 환경이면 "미검증"이라고 명시한다. 통과했다고 쓰지 않는다.

## 요약 표준 형식 (STATUS 항목, 커밋 본문, PR 본문 공통)
- 무엇을: 변경 내용 한두 줄
- 왜: 이유
- 영향 범위: 건드린 모듈, 호환성 영향
- 테스트: 실행한 것과 결과 (미검증이면 그렇게 적는다)
- 되돌리는 법: 커밋 revert, 설정 복원 등
- 검토 필요도: 낮음 | 중간 | 높음

## 작은 단위 원칙
한 커밋(PR)은 한 목적이다. 위험도가 다른 변경(예: 스타일 수정과 스키마 변경)은 섞지 않는다. 섞이면 전체가 높음으로 올라가 검토 부담이 커진다.
